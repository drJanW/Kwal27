WEB FREE-TEXT TTS PLAN

Date: 2026-04-07
Status: design only, no code yet

Goal
- Add free-text TTS in WebGUI modal dev/audio.
- Reuse the existing TTS playback chain.
- Do NOT reuse or hack calendar/today text as transport or storage.

Agreed Semantics
- Exactly one free-text TTS can be active at any time.
- Submit with non-empty text fully replaces the previous one.
- Submit with empty text clears/stops.
- Clear/stop icon also clears/stops.
- Clear/stop always means the same thing:
  - text removed
  - interval removed
  - duration/end-time removed
  - repeat timer cancelled
- Existing modal duration remains the lifetime of the free-text TTS.
- A new interval slider is added for how often the text is spoken.

Architecture Decision
- Use a parallel web workflow, not calendar/today.
- Web handler stores desired state in memory only.
- RunManager owns orchestration: replace, clear, create/cancel timer.
- AudioPolicy / PlaySentence remain the playback path.
- This is a single-slot scheduled TTS override, not a queue.

Why Not Calendar/Today
- Calendar already has its own meaning: day-derived sentence plus optional repeat interval.
- Free text from WebGUI is ad-hoc, temporary, and user-driven.
- Mixing them would create wrong ownership and reload side effects.

Preferred Data Model
- active: bool
- text: String
- intervalMs: uint32_t
- durationMs: uint32_t

repeatCount is computed locally in requestSet, not stored.

The state belongs with temporary web-audio control, not with calendar context.

Text Length Limits
- Soft UX goal: 99 characters.
- Hard backend max: 160 characters.
- Submit above 99 characters may still be accepted up to 160, but the UI should present 99 as the intended normal limit.
- Submit above 160 characters should be rejected or truncated consistently in firmware and UI.

Preferred Flow
1. User opens modal dev/audio.
2. User enters text, interval, and duration.
3. WebGUI sends one request.
4. Web route validates and forwards to RunManager.
5. RunManager clears previous free-text state if present.
6. If text is empty: stop here after clear.
7. Else store new state, speak once immediately, and create repeat timer.
8. On repeat timer fire, RunManager requests sentence playback.
9. On clear icon or empty submit, RunManager cancels timer and clears state.

Timer Strategy
- One timer only: cb_webFreeTextRepeat. No separate clear timer.
- Immediate speak happens outside the timer (before creating it).
- Compute repeatCount = durationMs / intervalMs, capped at 255.
- If repeatCount == 0: no timer needed; spoke once, done.
- If repeatCount > 0: create(intervalMs, repeatCount, cb_webFreeTextRepeat).
- Timer self-cleans after the last counted fire (repeat reaches 1 → slot deactivated).
  No manual cleanup, no second timer, no remaining() needed.
- State (text, intervalMs, durationMs) remains in memory after timer expires.
  Next requestSet or requestClear cleans it. Harmless until then.
- Replace (new text while active): requestClear cancels the timer,
  then requestSet stores new state and calls create().
  create() succeeds because cancel guarantees no active (cb, token) conflict.
- cancel() is safe on non-active timers — no guard needed in requestClear.

Pseudo-code: Route Layer

routeSetFreeTextTts(request):
  text = trim(request.text)
  intervalMs = parse/clamp interval
  durationMs = parse/clamp duration
  if text is empty:
    RunManager::requestClearWebFreeTextTts()
    return OK
  RunManager::requestSetWebFreeTextTts(text, intervalMs, durationMs)
  return OK

routeClearFreeTextTts(request):
  RunManager::requestClearWebFreeTextTts()
  return OK

Pseudo-code: RunManager Layer

requestSetWebFreeTextTts(text, intervalMs, durationMs):
  requestClearWebFreeTextTts()
  store text, intervalMs, durationMs
  mark active
  speak immediately once
  repeatCount = min(durationMs / intervalMs, 255)
  if repeatCount > 0:
    create(intervalMs, repeatCount, cb_webFreeTextRepeat)

requestClearWebFreeTextTts():
  cancel(cb_webFreeTextRepeat)
  clear text, intervalMs, durationMs
  mark inactive

cb_webFreeTextRepeat():
  speak stored text

Pseudo-code: UI Layer

onSubmit():
  text = textarea.value.trim()
  interval = intervalSlider.value
  duration = durationSlider.value
  send to set endpoint

onClearIcon():
  send to clear endpoint
  textarea.value = ""

UI Notes
- Stop icon should remain visible even when textarea is non-empty.
- Empty submit and clear icon should call the same backend clear behavior.
- UI label should make clear that interval = repeat frequency, duration = how long the free-text TTS stays active.

Rules To Preserve
- Web handlers: memory only, no blocking network or SD work.
- TimerManager only for timing.
- Prefer counted timers for constant intervals when the count fits in `uint8_t`.
- Do not use self-`restart()` for a constant interval repeat.
- Do not create a parallel TTS engine.
- Reuse existing speech pipeline.

Open Decisions
- Should submit speak immediately once, or wait until first interval tick?
  - Recommended: speak immediately once, then repeat by interval.
- Should currently playing free text interrupt fragment audio the same way other sentence requests do?
  - Recommended: yes, via existing sentence path.
- Should backend expose current text back to UI, or only active/interval/duration?
  - Recommended: expose at least active plus interval/duration; expose text only if useful in modal reopen.

Recommended Minimal Implementation Order
1. Firmware request and timer model in RunManager.
2. Web routes for set/clear.
3. Modal UI fields and clear icon.
4. JS wiring for submit and clear.
5. CSS only if the modal layout is not acceptable with existing styles.
6. SSE/WebGuiStatus only if later needed for state reflection after reload.

Summary
- This feature should be implemented as a single-slot scheduled web TTS override.
- New text fully replaces the old text.
- Empty submit and clear icon both map to the same clear/stop action.
- Calendar/today must remain separate.
